# Earth on Minecraft 现实仿真原则

## 1. 这份文档解决什么问题

Earth on Minecraft 不只复刻矿物和工业，也要复刻现实世界里人如何测量、建造、维修、运输、供能、生活和使用工具。以后新增内容不能只问“在 Minecraft 里能不能放下”，还要问：

1. 它在现实中是什么对象，依靠什么存在？
2. 它怎样和材料、能量、信息、空间发生关系？
3. 它需要接触、支撑、固定、供电、供料还是维护？
4. 失败时应该拒绝操作、显示故障、失去功能，还是产生可解释的破坏？

本体采用“现实因果优先、工程复杂度适度、MC 兼容出口保留”的路线。目标是让世界看起来和玩起来都像一个有原因的现实环境，不是把所有现实法规、危险和等待时间原样搬进游戏。

## 2. 三层规则

所有新内容先归入下面三层，避免把现实规则和硬核难度混在一起。

### 2.1 必须遵守的现实因果

这是本体的新内容默认必须遵守的底线：

- 物体不能无原因地悬空、穿插或瞬移到没有空间的位置。
- 工具必须作用于正确的目标，并且需要接触、方向、工作空间或合适的接口。
- 结构必须有地面支撑、基础、梁柱、墙体、锚固点、吊挂件或其他可解释的受力路径。
- 能源、物料和信息必须有来源、容量、连接和传递路径。
- 机器加工必须消耗输入、时间和必要的动力；副产物不能凭空消失。
- 管道、电缆、道路、轨道和输送设备必须有连续的连接或明确的端点。
- 设备和工具不能越过自身的尺寸、承载、功率、距离和材料适用范围。

### 2.2 为了可玩性而压缩的工程

以下内容可以抽象，但抽象后仍要保留现实方向：

- 一个方块可以代表一段墙、一个设备底座或一小段管道，不要求模拟每颗螺栓。
- 负载使用轻、中、重和超重等等级，不要求玩家计算真实牛顿和应力云图。
- 工艺时间、材料纯度、维护周期和流体体积可以按玩法倍率缩短。
- 复杂的控制系统用少量传感器、控制器和接口表达，不要求编写完整 PLC 程序。
- 物品可以继续堆叠、压缩和回到原版锭、块、工具与合成体系。

### 2.3 必须明确标出的例外

魔法、超自然能源、特殊维度和科幻材料可以突破现实规则，但必须满足以下条件：

- 例外由对象自身的标签或能力定义，不能让普通石头、木板、机器外壳突然获得悬浮能力。
- 手册、tooltip 或界面要说明它依靠什么特殊机制。
- 例外只改变自己负责的规则，不顺手让附近所有普通方块也失去支撑要求。
- 兼容模式可以保留原版行为，但应把它视作“游戏抽象”而不是现实规则。

## 3. 世界对象的分类

对象分类决定它默认采用什么规则。一个对象可以同时拥有多个标签，但每个标签的责任要清楚。

| 类别 | 现实含义 | 默认规则 |
|---|---|---|
| terrain | 基岩、山体、土层、沉积物、矿体 | 由世界生成的地质体可以作为天然整体；玩家挖空后进入支撑检查 |
| structural | 地基、墙、柱、梁、板、机架、桥体 | 需要支撑或锚固，并有承载等级 |
| loose_material | 沙、土、碎石、矿堆、填土 | 需要坡面、挡墙、容器或其他约束；不能像实心梁柱一样无限悬挑 |
| equipment | 机器、泵、发电机、起重设备、工具台 | 需要安装空间、基础、动力或工艺接口 |
| utility | 管道、电缆、道路、轨道、输送机 | 需要端点、连续路径、方向和容量 |
| fixture | 灯具、阀门、仪表、门窗、护栏 | 需要墙、顶、地面或专用安装面 |
| temporary_support | 脚手架、模板、施工支架、吊具 | 可以暂时承受或定位对象，但有阶段和拆除条件 |
| floating_exception | 明确的浮空岛、魔法锚、特殊气囊结构 | 只有对象自己声明后才能脱离普通支撑规则 |
| decoration | 画、标牌、非承重装饰面 | 需要挂接面，但不承担结构荷载 |

## 4. 支撑与重力规则

### 4.1 支撑不是“正下方一格”

现实建筑依靠的是受力路径，而不是每个方块都必须直接压在下方方块上。系统应把相邻对象组成支撑图：

- 节点是单块、连续方块组或已成型的多方块结构。
- 边表示压承、拉结、侧向支撑、嵌固、吊挂、基础连接或设备固定。
- 每个节点有自重等级、承载能力和允许的连接方向。
- 支撑图必须能从对象追溯到地面、天然岩体、基础、锚固点或明确的悬挂源。

因此，以下结构可以成立：

- 柱支撑的楼板和屋顶。
- 两端落在墙或柱上的梁与桥面。
- 由多块组成并有足够厚度的拱和洞顶。
- 固定在墙面、屋顶或电线杆上的灯具和仪表。
- 由钢索、吊杆或专用支架悬挂的设备。
- 有地基和框架的多方块机器。

以下结构默认不能成立：

- 普通泥土、石头、机器外壳或道路方块从空中开始连续延伸。
- 没有锚固点的灯、管道、平台和重型设备悬在空中。
- 破坏唯一基础后，整台机器仍继续工作且没有故障状态。
- 把装饰贴面当成承重梁，把薄板当成完整实体支柱。

### 4.2 建造时和破坏后的处理

支撑检查采用事件驱动，不做每 tick 全世界物理计算。至少在下列事件后重新检查受影响的局部结构：

- 放置或破坏结构方块。
- 机器成型、拆解、移动或改变方向。
- 爆炸、坍塌、地形迁移或旧存档加载。
- 施工脚手架、模板或吊具被移除。

第一阶段默认使用安全处理：

- 新放置对象没有合法支撑时拒绝放置，并提示缺少地基、梁柱、锚固点或安装面。
- 已存在的旧建筑不因升级或加载立刻被删除。
- 被破坏而失去支撑的设备先变为 unstable 或 fault，停止承担功能并显示维修入口。
- 真正的掉落、断裂和坍塌属于可选结构完整性模式，必须有预览、延迟和关闭选项。

这保证现实规则可以逐步加入，又不会因为一次版本升级摧毁玩家存档。

### 4.3 松散材料与固体结构不同

沙、土、碎石、矿堆和填土不是可以随意悬挑的梁柱。它们应当使用坡度、挡墙、容器、压实层或结构框架表达稳定性。第一阶段可以把复杂的颗粒流抽象为几个结果：

- 有坡面或挡护：保持稳定。
- 有施工支架：暂时保持稳定。
- 失去约束：显示不稳定、禁止继续堆高，或在可选模式下转为下落物/滑落体。

## 5. 现代工具的统一规则

现代工具不是“换一张贴图的右键合成器”。每种工具至少要定义六个要素：

1. **目标**：木材、岩石、金属、管件、线路、土壤、流体或测量对象。
2. **接触方式**：手持接触、贴靠安装、远距离测量、夹持、钻孔、切割或连接。
3. **工作空间**：工具前方、顶部、侧面或设备内部必须有可用空间。
4. **动力与耗材**：人力、电力、燃料、刀片、钻头、焊材、润滑剂或校准件。
5. **能力边界**：最大硬度、尺寸、重量、距离、温度、压力或精度。
6. **结果**：改变目标、产生材料、建立连接、给出读数、产生故障或拒绝操作。

建议的现实工具路线包括：

| 工具或设备 | 现实作用 | 仿真要求 |
|---|---|---|
| 卷尺、水平尺、测距仪 | 尺寸、水平、距离和坡度测量 | 读取真实方块坐标和表面，不直接创造或移动方块 |
| 地质锤、取样器、钻机 | 取样、钻孔、识别岩层 | 需要目标接触、合适材料和耗材；产出样品或孔洞 |
| 锤子、扳手、钳子 | 敲击、紧固、拆卸、装配 | 只作用于对应紧固件、管件、结构件或工具台 |
| 锯、切割机、钻床 | 切割和加工 | 需要工作台、夹持、刀具和安全空间；不能隔空改造整面墙 |
| 焊机、铆接工具 | 永久连接金属件 | 需要电力/焊材和相邻金属对象；结果是连接强度或维修状态变化 |
| 泵、阀门、压力表、流量计 | 传输和测量流体 | 必须接入连续管路；断路、满载和超压要反馈为状态 |
| 起重机、叉车、吊具 | 搬运重物 | 需要地面、额定载荷、作业半径和可通行空间 |
| 万用表、传感器、控制器 | 测量电气和过程参数 | 需要接触端子或传感点；读数来源必须对应真实设备状态 |

工具可以用右键作为操作入口，但右键只代表“发出操作请求”。最终结果必须经过目标、接触、空间、材料、动力和能力边界检查。

## 6. 工具之外的现实世界内容

本体后续不按“继续堆工业机器”的单一路线扩展，而是按现实活动组织内容：

- **测量与科学**：地质、气象、水文、材料检验、长度、角度、温度、压力、流量、湿度和电气测量。
- **建造与维护**：地基、道路、墙体、屋顶、门窗、管廊、脚手架、维修、替换件和施工顺序。
- **家庭与公共设施**：照明、给排水、供暖、通风、卫生设施、仓储、道路标识和垃圾回收。
- **农业与土地**：土壤改良、播种、灌溉、排水、温室、农机和盐碱地修复；不把人体生理难度强塞进本体。
- **交通与搬运**：手推车、叉车、吊装、道路、轨道、码头、仓库和装卸接口。
- **通信与信息**：电话、电台、光纤、仪表板、传感网络、记录、定位和控制信号。
- **维修与应急**：断路、堵塞、泄漏、磨损、备件、更换、隔离和恢复；危险程度可以先安全化表达。
- **生活与健康**：与人物状态、疾病、营养和医疗有关的内容继续通过 Earth Human 等独立模块联动。

每个新内容切片至少要形成“对象 -> 工具/设施 -> 可见结果”的闭环。例如：湿地土壤 -> 取样器和水分计 -> 排水沟与改良材料；道路损坏 -> 测量工具和维修车 -> 沥青、压实和恢复通行；管线堵塞 -> 压力表和检修口 -> 定位、拆换和恢复流量。

## 7. 空间、连接与因果检查

所有新方块、工具和机器都要通过以下检查：

| 检查 | 失败时的现实表现 |
|---|---|
| 空间占用 | 无法安装、需要清理空间或显示碰撞冲突 |
| 支撑/锚固 | 无法放置、结构不完整或进入不稳定状态 |
| 接触面 | 工具无法作用、仪表无读数、设备无法安装 |
| 连接路径 | 断路、断管、断轨、断输送或显示未连接 |
| 容量 | 满仓、满罐、堵塞、过载或需要旁路 |
| 能源 | 待机、欠压、断电、燃料不足或热量不足 |
| 工具能力 | 材料过硬、距离过远、负载过重、温压超限 |
| 时间与维护 | 处理尚未完成、需要冷却、磨损或更换部件 |

这些检查必须在界面、tooltip、手册和日志中使用同一套状态词，不能只给玩家一个模糊的“失败”。

## 8. 数据驱动实现约定

后续实现优先使用标签和数据定义表达规则，Java 只负责通用求解和状态传播。建议为对象逐步补充以下数据维度：

- support_profile：支撑来源、连接方向、承载等级、是否可悬挂。
- mounting_profile：地面、墙面、顶部、导轨或设备接口要求。
- load_profile：自重、静态负载、动态负载和允许的悬挑距离。
- tool_profile：目标标签、接触方式、耗材、动力和能力上限。
- utility_profile：管道、电缆、道路、轨道或输送的端点与容量。
- process_profile：输入、输出、副产物、时间、动力和故障条件。
- spatial_profile：占用空间、检修空间、工作面和安全距离。

实现顺序应是：先定义规则和状态，再做代表性对象，最后扩大到全体方块。没有状态闭环的模型、贴图或配方不能算作已完成的现实功能。

## 9. 测试基线

第一批结构与工具系统至少要覆盖这些行为：

1. 普通机器外壳不能从空中放置；有地基和机架后可以成型。
2. 两端有支撑的梁可以悬挑一段；超过能力边界时进入不稳定状态。
3. 顶部吊灯、墙面仪表和管道必须有对应安装面。
4. 破坏唯一基础后，设备停止工作并给出维修或重新支撑提示。
5. 脚手架可以支撑施工阶段，拆除前必须完成转固或显示风险。
6. 扳手不能代替钻机、锯或测量工具；工具目标不匹配时不消耗关键材料。
7. 断开的电缆、管道和输送机不会继续传输，只显示断路或未连接。
8. 满容量、超载、缺动力、空间不足和工具过载都能在界面中区分。
9. 旧存档加载时先标记问题并提供修复路径，不直接无预警删除方块。
10. 明确标记为 floating_exception 的对象可以悬浮，但普通石头、泥土、机器和道路不继承该例外。

## 10. 开发优先级

1. 固化对象分类、状态词和 support_profile/mounting_profile 数据格式。
2. 为机器、道路、管道、灯具和基础结构实现局部支撑与连接检查。
3. 加入测量、维修、装配和检修工具，先做工具能力边界与可见反馈。
4. 将公共工程、交通、农业、水务、通信和回收做成小型完整切片。
5. 再评估可选的结构完整性、坍塌、磨损、泄漏和应急模式。

本体的验收标准是“现实原因可追溯、结果可观察、失败可修复、兼容出口仍存在”。只有增加材料名称而没有空间、工具、连接或维护语义的内容，不进入优先开发队列。
