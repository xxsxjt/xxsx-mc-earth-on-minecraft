# Machine layer: legacy fixes and spec routes

Date: 2026-10-27

## Legacy machine defects found and fixed

| Defect | Impact | Fix |
|---|---|---|
| `Recipe` held a single `Supplier<ItemLike>` input | 223 two-input and 46 three-to-five-input spec routes could not run | `Recipe` now carries an ordered `List<Input>`; the first entry selects the route, the rest are consumed from additive slots |
| Only one generic secondary input existed, and it was the coke-only reagent slot | Any route needing a second reagent was unrunnable | `SLOT_SECONDARY_START` + 4 additive slots; the coke reagent slot remains separate and unchanged |
| Both `data` slots and the tick loop used `kind.processTicks()` | Every route on a machine ran for one fixed duration even though the spec declares 40-2400 ticks per route | `Recipe.processTicks()` / `energyPerTickEffective()` override the machine defaults when the route declares them |
| `processTicks` in the menu progress bar ignored the running route | Progress bar showed the wrong denominator for spec routes | `data[1]` now reports the active route's duration |
| `MachineInterfaceBlockEntity.INPUT_SLOTS` hard-coded three slots | Automation interfaces could not feed additive slots | Interface input slot list is derived from the machine's slot layout |
| JEI drew one input slot | Multi-input routes looked like single-input routes in JEI | JEI renders every declared input and offsets the coke slot |
| Screen had no state for missing additives | Players saw a generic "unsupported" or "output blocked" status | New `missing_additive` UI state plus zh/en strings and a rendered preview |
| Save format assumed the reagent slot sat right after the output row | Moving the additive slots would have silently eaten stored coke | `SlotLayoutVersion` is written; older saves migrate their reagent stack into the new slot |

### Authored chains

The spec leaves several whole families as placeholders: it names the item, gives a
`family:...` or `gather:...` pseudo-source, and ships no producer. Five generators fill those in.
They write `earth/quality/*_routes.json`, and `generate_spec_machine_recipes.py` merges every
file it finds there into the same table, so JEI and the machines see one route list.

| Generator | Output | Routes | Why the spec could not supply them |
|---|---|---|---|
| `generate_drink_routes.py` | `drink_routes.json` | 83 | 70 drinks declared as `family:drink` with no producer |
| `generate_medicine_routes.py` | `medicine_routes.json` | 70 | 68 medicines declared as `family:medicine` with no producer |
| `generate_herb_routes.py` | `herb_routes.json` | 136 | 136 herbs declared as `gather:wild_herb` only |
| `generate_crop_routes.py` | `crop_routes.json` | 129 | 129 crops declared as `agriculture:crop` only |
| `generate_wild_herbs.py` | loot modifiers + loot tables | 136 herbs | no plant block, no worldgen, no loot |

`herb_routes` and `crop_routes` are propagation routes: one unit plus a nutrient input yields two,
so the chain is renewable once the player owns the first unit. `generate_wild_herbs.py` supplies
that first unit by adding a 12.5% drop to short grass, fern and large fern.

Every material referenced by these generators was checked against `spec/eom/items.jsonl`; a
validator (`tools/_validate_generated_routes.py`) fails the build if a route names an unregistered
item or an unknown machine kind.

### The 64 KB method limit

`SpecMachineRecipes` exceeded javac's 64 KB method-body limit at 819 routes and failed to compile
("code too large"). The generator now emits the table as chunked `addN(List<Route>)` helpers of 100
routes each, called from `buildRoutes()`. Any further growth is absorbed automatically.

Registered machines: the 21 original processing machines plus the 30 spec recipe stations
(`anvil`, `bar_counter`, `campfire`, `carpentry_bench`, `casting_table`, `coffee_roaster`,
`condenser`, `converter`, `curing_barn`, `fermenting_crock`, `filter_press`, `gem_cutter`,
`herb_processing_table`, `loom`, `mill`, `noodle_press`, `oil_press`, `rice_huller`, `smelter`,
`smokehouse`, `steamer`, `steamer_basket`, `still`, `stone_mill`, `stove`, `tablet_press`,
`tannery`, `tea_kiln`, `thickener`, `water_treatment_unit`).

## Multiblocks

The six spec multiblocks are now real machines, not decorative blocks. Each controller is a
`ProcessingMachineBlock` and carries its own `MachineMultiblock.Pattern`.

| Multiblock | Controller | Size | Pattern |
|---|---|---|---|
| Bloomery | `bloomery_controller` | 3x4x3 | `BLOOMERY` |
| Bread oven | `bread_oven_controller` | 3x3x3 | `BREAD_OVEN` |
| Glass kiln | `glass_kiln_controller` | 3x4x3 | `GLASS_KILN` |
| Lime kiln | `lime_kiln_controller` | 2x4x2 | `LIME_KILN` |
| Charcoal pit kiln | `pit_kiln_controller` | 3x3x3 | `PIT_KILN` |
| Shaft furnace | `shaft_furnace_controller` | 3x5x3 | `SHAFT_FURNACE` |

Layer patterns come straight from `spec/eom/multiblocks.jsonl`: `B` shell (firebrick, clay
brick, packed earth), `#` interior air, `C` controller, `T` tuyere, `A` air inlet, `O` oven
mouth, `H` chimney, `.` no requirement. `MachineMultiblock.buildLayeredRequirements` expands
them relative to the controller and tries all four horizontal facings, like the industrial
patterns. Every kiln uses `PowerMode.HEAT_ONLY`, so it keeps a fire going even at zero draw.

The 28 spec multiblock routes are wired: 3 bloomery, 2 bread oven, 6 glass kiln, 3 lime kiln,
1 pit kiln and 13 shaft furnace routes.

## Power semantics for the new stations

`PowerMode` now models the spec `power` arrays with four independent flags: `grid`, `fuel`
(fuel slot accepts burnables), `heat` (needs a burning fire), `manualFallback` (hand, crank,
water wheel or animal drive can replace missing supply), and `passive` (ambient process).

| Mode | grid | fuel | heat | manual | passive |
|---|---|---|---|---|---|
| `LOCAL_OR_GRID` | yes | yes | no | no | no |
| `HEAT_OR_GRID` | yes | yes | yes | no | no |
| `GRID_ONLY` | yes | no | no | no | no |
| `MANUAL_OR_HEAT` | no | yes | yes | yes | no |
| `MANUAL_OR_GRID` | yes | no | no | yes | no |
| `KINETIC` / `MANUAL` | no | no | no | yes | no |
| `HEAT_ONLY` | no | yes | yes | no | no |
| `PASSIVE` | no | no | no | no | yes |

The tick loop resolves supply in that order: passive, grid draw, fuel fallback, fire requirement,
manual fallback. A route that finds none of them stalls with no fuel consumed.

- `HEAT_ONLY` stations (campfire, stove, steamer, smokehouse, still, ...) consume fuel even though
  their electric draw is zero, so the fire has to be kept going.
- `MANUAL`, `KINETIC`, `MANUAL_OR_HEAT` and `MANUAL_OR_GRID` routes run without fuel or grid power.
- `PASSIVE` (fermenting crock) never needs either; the process is ambient.
- `ProcessingMachineMenu.needsExternalPower()` drives the screen warning, so manual and passive
  routes no longer show a false "missing power" state.

## Fluid tank

Each processing machine owns one `MachineFluidTank` (`TANK_CAPACITY` = 8000 mB) holding a single
fluid. It is exposed through `Capabilities.Fluid.BLOCK` on every side, so pipes, buckets and
hoppers can fill or drain it.

- `MachineFluidTank` implements `ResourceHandler<FluidResource>` and fires a listener on every
  mutation, which mirrors the amount and fluid id into `DATA_TANK_AMOUNT` / `DATA_TANK_CAPACITY`
  for the screen.
- The tank is persisted with `TankFluid` / `TankAmount` in `saveAdditional`.
- Routes declare `FluidInput` / `FluidOutput` amounts in mB; a route with fluid output is blocked
  while the tank is full or holds a different fluid, so the product is never voided.
- 16 fluid-only routes (14 `casting_table` molten-metal casts, `condenser`, `thickener`) have no
  primary item. When the input slot is empty the block entity resolves them from the tank contents
  via `ProcessingMachineBlock.fluidOnlyRecipes`; a change of stored fluid also resets the selected
  route index.
- The screen draws a tank gauge at `(58, 18)` and reports `missing_fluid` when the selected route
  needs more fluid than the tank holds.

## Still open

- 5 machines remain unregistered because the spec gives them no live routes (`autoclave`,
  `herb_dryer`, `pharmacy_table`, `sorter`) or only a retired one (`electrolysis_brine`). All five
  are still `planned` in `spec/eom/machines.jsonl` with empty `recipes`, so registering them would
  add empty shells; they stay out until the spec supplies routes.
- `automation_bus`, `robotic_arm` and `sorter` are logistics devices, not processing machines: the
  spec gives them `recipes: []` because they move items rather than transform them. They are not
  blocked on missing routes; they need their own block entity behaviour, which does not exist yet.
- 129 registered items still have no producer of any kind. Breakdown: chemical 37, misc 22,
  food 13, intermediate 12, life 12, raw material 9, metal 5, power 4, medicine 4, drink 3,
  machine part 3, gem 2, one each of tool/agriculture/tobacco. Run
  `python tools/_dead_content.py` for the current list; the metric fell from 256 to 129 when the
  herb and crop chains landed.
- No `LiquidBlock` or bucket exists for the 30 spec fluids; they are tank-only for now
- `SpecMachineRecipes` routes resolve registry ids lazily; they are built on first access after
  registration, so any future eager call must stay behind the lazy table
